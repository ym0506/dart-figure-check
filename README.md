# dart-figure-check

사업보고서(DART)의 재무 표에서 LLM이 옮겨 적은 숫자를 받기 전에 무엇을 확인해야 하는지 재 보는 작은 실험입니다.

앞선 프로젝트(미국 10-K로 투자안을 심사하는 에이전트)에서 쓴 검사는 인용이 원문에 글자 그대로 있고 그 안에 같은 숫자가 있으면 값을 받았습니다.
이 검사는 **같은 인용 안의 다른 숫자**(예: 당기 대신 전기)를 고른 오류를 거르지 못했습니다. 재무 표는 한 행에 당기와 전기 숫자가 나란히 있어서
이 오류가 생기기 쉬운 자리입니다. 그래서 표의 칸 위치까지 확인하는 검사를 만들고 한국 공시로 시험했습니다.

## 무엇을 재나

- **정답**: 사람이나 AI가 적은 정답표 대신 DART 공식 재무 데이터(`fnlttSinglAcntAll`, 연결, 2025 사업보고서)의 당기·전기 금액(원).
- **표본**: 2026년 3월에 접수된 유가증권시장 사업보고서(2025 회계연도, 정정 제외)를 접수번호 순으로 보며 대상 계정 6개
  (매출액, 영업이익, 당기순이익, 자산총계, 부채총계, 자본총계)가 공식 데이터에 모두 있는 회사를 앞에서부터 10곳(개발용).
  같은 규칙으로 그다음 20곳(처음 보는 회사)을 따로 두었습니다.
- **원문 읽기**(`parse.py`): `document.xml`의 본문 XML을 표준 라이브러리 `html.parser`로 관대하게 읽고 표마다 병합 칸을 풀어 칸 위치(T표R행)를 남깁니다.
  단위는 표 앞의 '(단위 : 백만원)' 같은 문구로, 당기·전기 열은 머리글의 기수(제 N 기)나 연도가 큰 열부터 코드가 정합니다.
- **검사 두 가지**(`verify.py`)
  - P1 인용과 숫자 대조: 인용이 원문 줄에 그대로 있고 인용 안에 같은 숫자가 있으면 받습니다. 값과 단위는 LLM이 말한 대로 씁니다.
  - P2 표 칸 확인: 인용과 글자가 같은 줄을 코드가 찾고(LLM이 적은 위치는 자주 틀려서 인용이 우선), 그 줄이 연결재무제표 표에 있는지,
    행 이름이 계정별 이름 목록과 정확히 같은지, 그 행의 해당 기간 열 숫자가 LLM 값과 같은지 봅니다.
    최종 금액은 코드가 칸에서 읽은 숫자 × 표 단위로 계산합니다. LLM이 적은 단위는 쓰지 않습니다.
- **오류 주입**(`inject.py`, API 없음): 올바른 답에 6가지 오류를 넣고 각 검사가 틀린 값을 몇 번 통과시키는지 셉니다.
- **검색 비교**(`retrieve.py`, API 없음): 덩어리를 나누는 방식에 따라 정답 행이 BM25 상위 k개 안에 드는지.
- **LLM 추출**(`extract.py`): 요약재무정보와 연결재무제표 표를 통째로 주고 계정 6개 × 당기·전기 12칸을 받습니다.
  Claude(Haiku 5.5) 또는 로컬 모델(Ollama)로 돌릴 수 있습니다.

## 실행

```bash
python3 -m venv .venv && .venv/bin/pip install opendart-py==0.1.0 anthropic pytest
.venv/bin/python -m pytest -q
.venv/bin/python -m dartcheck.fetch 10                 # 개발용 10곳. DART 키: ~/.config/opendart/.env 의 DART_API_KEY
.venv/bin/python -m dartcheck.fetch 20 10 holdout      # 그다음 20곳
.venv/bin/python -m dartcheck.run parse                # 정답 칸을 원문 표에서 찾았는지
DARTCHECK_SAMPLE=holdout .venv/bin/python -m dartcheck.run parse
.venv/bin/python -m dartcheck.run inject               # 오류 주입
.venv/bin/python -m dartcheck.run recall               # 검색 비교
DARTCHECK_LOCAL_MODEL=granite3.3:8b DARTCHECK_MODES=통째로 DARTCHECK_WORKERS=1 .venv/bin/python -m dartcheck.run llm
.venv/bin/python -m dartcheck.run score                # LLM 결과 채점
```

내려받은 공시 원문은 `data/raw/`에만 두고 저장소에 넣지 않습니다. DART 호출은 [opendart-py](https://github.com/TreasurerSquad/opendart-py) 0.1.0을 씁니다.
원문 zip은 본문과 첨부(감사보고서 등) 파일 여럿인데 `get_document`는 전부 이어 붙인 글을 돌려줘서, 본문 파일만 쓰려고 클라이언트의
내부 요청 함수(`_request`)로 zip을 받습니다.

## 결과 (2026-11-16)

### 원문 읽기

개발용 10곳(진양산업, 대한유화, 국도화학, 현대모비스, 케이씨씨, 삼성전자, 하이스틸, 유니드, 삼성SDI, 제일기획)의 정답 120칸
(10곳 × 계정 6개 × 당기·전기)을 모두 원문 표에서 찾았고, 칸 숫자 × 표 단위가 공식 금액과 표 단위 하나 이내로 같았습니다.
단위는 원(8곳)과 백만원(2곳)이 섞여 있었습니다. 같은 규칙으로 앞에서 만난 4곳(진양화학, 인천도시가스, 미원화학, 롯데리츠)은
공식 연결 데이터가 없어 빠졌습니다.

처음 보는 20곳(한화투자증권, 삼성에스디에스, LG디스플레이, 농심, SK리츠 등, `data/raw/holdout.json`)은 행 이름 목록과 코드를 고치지 않고 돌렸습니다.
240칸 중 238칸을 찾았고 찾은 칸은 당기·전기 모두 공식 금액과 같았습니다. 놓친 2칸은 GS피앤엘의 '매출액 및 지분법이익' 행(당기·전기)으로,
정확히 비교하는 이름 목록에 없는 이름이었습니다. 이 회사에서 LLM이 맞는 행을 가리켜도 P2는 거부합니다(오거부). 결과: `results/inject_gold_holdout.json`.

### 오류 주입 (`results/inject_gold.json`)

올바른 답 120개는 정답 칸에서 코드로 만들었습니다. P1과 P2 모두 120개를 받습니다.

| 넣은 오류 | 넣은 수 | P1 인용과 숫자 대조 | P2 표 칸 확인 | P2, 이름을 부분 문자열로 비교할 때 |
|---|---|---|---|---|
| 당기와 전기 바꿔치기 | 120 | 120 통과 | 0 | 0 |
| 연결 대신 별도재무제표 값 | 120 | 120 통과 | 0 | 0 |
| 같은 표의 다른 행 | 120 | 119 통과 | 0 | **29 통과** |
| 단위를 잘못 적음 | 120 | 120 통과 | 0 (표 단위로 교정) | 0 |
| 숫자 한 자리 틀림 | 120 | 0 | 0 | 0 |
| 음수 부호 빠짐 | 7 | 0 (부호를 무시하면 7) | 0 | 0 |

읽는 법
- 오답을 만드는 함수와 P2가 검사에 쓰는 함수가 같아서 P2 열의 0은 설계대로 나오는 값입니다. 명세 시험으로 봐 주세요.
- 정보가 있는 숫자는 두 가지입니다. P1이 이 오류들을 거의 전부 통과시킨다는 것, 그리고 처음 만든 P2(행 이름을 부분 문자열로 비교)가
  '매출원가'를 매출액으로, '부채와자본총계'와 '부채및자본총계'를 자본총계로, '지배기업의 소유주에게 귀속되는 당기순이익(손실)'을
  당기순이익으로 받아 120건 중 29건을 통과시켰다는 것입니다. 주석 번호를 뗀 이름이 계정별 목록과 정확히 같아야 받게 바꿨습니다.
  처음 보는 20곳에서도 부분 문자열 비교는 틀린 행 238건 중 48건을 통과시켰고, 정확한 비교는 0건이었지만 위 2칸을 놓쳤습니다.
- '같은 표의 다른 행' 1건은 옆 행(지배기업 귀속 당기순이익)이 그해 당기순이익과 같아 틀린 값이 아니었습니다.

### 검색 비교 (`results/recall.json`)

정답 행(요약재무정보나 연결재무제표에서 행 이름이 맞고 당기 칸이 공식 금액과 같은 행)이 BM25 상위 k개 덩어리 안에 든 계정 수.
분모 60 = 10곳 × 계정 6개(당기 행). 검색어는 계정마다 고정 문구(예: '연결 손익계산서 매출액 수익'), 낱말은 글자 2개씩 끊어 셉니다.

| 덩어리 | 상위 1 | 상위 3 | 상위 5 | 상위 10 |
|---|---|---|---|---|
| 행 단위, '재무에 관한 사항' 전체 | 17 | 28 | 31 | 31 |
| 1,000자 고정(200자 겹침), 전체 | 23 | 34 | 36 | 51 |
| 행 단위, 요약재무정보와 연결재무제표 섹션만 | 34 | 36 | 52 | 60 |

처음 보는 20곳(분모 119, GS피앤엘 매출액 제외)에서는 상위 5개 기준 53, 70, 104, 상위 10개 기준 58, 98, 116이었습니다(`results/recall_holdout.json`).

'재무에 관한 사항'에는 회사마다 표가 300~1,600개 있고 주석과 별도재무제표에도 '매출액' 행이 많습니다.
셋째 줄은 정답이 있는 섹션으로 검색 범위를 줄인 것이라 청킹 방식보다는 섹션 제목(메타데이터) 거름의 효과입니다. 임베딩 검색과 리랭커는 아직 비교하지 않았습니다.

### LLM 추출

아직 결과가 없습니다. 로컬 Granite 3.3 8B(Ollama, Apple M2 Pro 16GB)로 10곳을 시도했지만 한 건에 3~6분씩 걸리다 메모리 여유가 4%까지
떨어져 3곳에서 멈췄습니다. 시험 삼아 돌린 첫 건(진양산업)에서는 당기 6칸은 맞혔고 전기 6칸은 원문에 없는 어림수와 인용을 지어내
P1에서 모두 걸렸습니다. LLM이 실제로 얼마나 자주 기간이나 별도 표를 헷갈리는지, P2가 맞는 답을 얼마나 거부하는지는 Claude나 더 큰 모델로
`run llm`을 돌려야 알 수 있습니다(결과는 실행마다 바로 저장되게 바꿨습니다).

## 한계

- 계정 6개는 공식 데이터로도 받을 수 있는 가장 쉬운 숫자입니다. 이 실험은 공식 데이터가 있는 곳에서 검사기를 시험한 것이고,
  주석 표, 부문 정보, 분기보고서, 금융회사처럼 머리글에 기간 표시가 없거나 행 이름이 제각각인 표에서는 P2의 가정이 깨질 수 있습니다.
- 표 단위를 잘못 읽으면 P2는 틀린 값을 그대로 내보냅니다. 단위는 LLM이 아니라 코드가 읽으므로 원문 읽기 결과(정답 칸 일치)로만 확인했습니다.
